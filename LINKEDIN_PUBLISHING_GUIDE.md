# LinkedIn Publishing Guide

The strongest posts from this roadmap should show evidence, not only announce that a day is complete. Publish two or three useful posts per week rather than 114 nearly identical updates.

## Recommended post structure

1. **Hook:** the problem you solved in one sentence.
2. **Context:** what the system was meant to do.
3. **Build:** three concrete decisions or commands, explained simply.
4. **Failure:** what broke and which evidence revealed the cause.
5. **Result:** a measurable outcome, screenshot, diagram, or repository link.
6. **Question:** invite practitioners to compare approaches.

## Reusable post template

```text
Day [NNN]/114 — [TOPIC]

Today I built [ONE CONCRETE THING] instead of only reading about it.

The useful mental model:
• [IDEA 1]
• [IDEA 2]
• [IDEA 3]

What failed: [REAL CONTROLLED FAILURE]
How I diagnosed it: [LOG / METRIC / COMMAND / TEST]
What I changed: [FIX]
How I verified recovery: [OBJECTIVE RESULT]

Code, runbook and cleanup steps: [REPOSITORY LINK]

How would you test this before production?

#DevOps #[TOPIC_TAG] #Linux #CloudEngineering #LearningInPublic
```

## Evidence to attach

- one clean architecture or request-flow diagram;
- one readable terminal screenshot with private data redacted;
- a short before/after metric or test result;
- a direct link to the day's `notes.md` or project—not only the repository home page.

## Four-week rhythm

- **Tuesday:** a lesson with a diagram and plain-language explanation.
- **Thursday:** a failure/recovery story from Project 2.
- **Saturday:** a weekly build recap with links to completed work.
- Spend time replying thoughtfully to relevant engineering discussions; avoid automated or generic comments.

## Profile positioning

Use a headline that states role, strengths, and proof, for example: `DevOps Engineer | Linux, Kubernetes, Terraform & CI/CD | Building a public 114-day production roadmap`. In Featured, pin the roadmap, the capstone, and one strong incident/runbook post. Keep claims accurate and let working projects demonstrate competence.

Never publish client/employer information, real secrets, internal hostnames, private dashboards, or unredacted incident data.
